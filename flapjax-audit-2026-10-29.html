First-BNB-funder trace for each recipient

The task asks who first sent each recipient BNB. This was checked directly against historical account state on a BSC node, not from a block explorer’s labels: for each address the BNB balance was binary-searched across blocks 1 to 130605332 to find the first block in which its balance was non-zero, and current balance and transaction count (nonce) were read at the chain head. The nonce matters: an address that has never sent a transaction has nonce 0, so it cannot have spent any BNB it received.

Recipient 1: 0xab39... (3,000,000 FLAPJAX) — one first funder found

  • Address: 0xab39aa1e2db4036e01cf7e919b3f239b3ff90160
  • Balance was 0 BNB at block 128594174 and 148,891,209,770,897 wei at block 128594175, the first block in which it held any BNB. That is about 0.000149 BNB.
  • The BNB arrived by internal transfer inside transaction 0x4ebb6e4d…49e79, which is the only transaction in that block whose calldata names this address. The outer transaction was sent by 0x4337031ade3a53d10121f350369907076b6d32a4 (an EOA) to 0x0000000071727de22e5e9d8baf0edac6f37da032, an ERC-4337 account-abstraction bundler. The call data carries the recipient address and the amount 0x876a6fab2791 = 148,891,209,770,897 wei, matching the balance change exactly.
  • The address that actually paid out that BNB is the smart account 0xc1ea672cf70891a2c73e536963ecb11168eb570a (12 bytes of runtime code), which is the account the bundler executed for. So the first funder is that smart account, not a plain wallet.
  • Block 128594175 is timestamped 2026-10-19 12:28:03 COT — ten days before it was paid.
  • At the chain head this address still holds BNB and has nonce 5, so it has sent 5 transactions; it is an active wallet, not a passive collector.

Recipients 2, 3 and 4: no BNB funder exists to find

These three addresses have never held any BNB and have never sent a single transaction. Sampled at blocks 1,000,000 / 20,000,000 / 60,000,000 / 90,000,000 / 110,000,000 / 120,000,000 / 125,000,000 / 128,000,000 / 129,000,000 / 130,000,000, at the first block of the audited day, and at its last block, every historical BNB balance reads exactly 0. Their nonce is 0 at the chain head, and none of them has any contract code.

This is a real finding rather than a gap in the trace. A wallet whose balance is zero at every point in time and whose nonce is zero has never received BNB, so there is no first funder to name, and no funder transaction to link. They could receive FLAPJAX because FLAPJAX transfers need no gas from the recipient. The consequence for grouping is stated below.

Does any recipient share a first funder with another, or with the treasury?

No two recipients share a first funder, because only one recipient has a funder at all.

  • The treasury’s own first BNB came from 0x5ba434b40be6cfc7033bf8d4545320fa609a4268 in transaction 0xe0f7aeee…9bfd0 (0.000126 BNB, block 123473817). That funder is not the funder of any recipient.
  • Recipient 1’s funder, the smart account 0xc1ea672c…570a, is not the treasury’s first funder.
  • Recipients 2, 3 and 4 have no funder, so they cannot be grouped with anyone by funding.

Distinct operators implied by the funder groups: 4. Five transfers, four distinct recipient addresses, four distinct funding identities, since three of the four are wholly unfunded and the fourth was funded by its own separate smart account.

What this audit cannot conclude. The funder trace is only evidence of shared control when a funder exists. Three of these four wallets are unfunded and dormant, so this method says nothing about whether they are controlled by the same operator through some other means. They are grouped as four only in the narrow sense the task defines: no shared first BNB funder. If the same operator generated these addresses and paid out FLAPJAX without ever needing gas in them, the funding trail would not reveal it.

Transfers I could not fully explain

  • All 5 transfers are fully explained as to amount, sender, recipient, block and time.
  • Recipients 2, 3 and 4 have no explanatory funding transaction, for the reason given above: they never held BNB.
  • Recipient 1’s funding is explained, but its first funder is an ERC-4337 smart account rather than a plain wallet, so “the wallet that first sent it BNB” resolves to a contract-mediated internal transfer. Traces are not exposed on the free public BSC nodes used here, so the internal transfer was read from the transaction’s calldata and the exact balance delta rather than from a trace call; both agree to the wei.

Method and reproduction

  1. Resolve the COT day boundaries to blocks by timestamp: 130413458 (00:00:00 COT) and 130605332 (23:59:59 COT).
  2. Page eth_getLogs over 130413458 to 130605332 in 10,000-block spans for the token contract with topic0 = the ERC-20 Transfer signature 0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef. That returns 29 transfer events in the window.
  3. Keep only events whose topics[1] (from) is the treasury, zero-padded. That leaves the 5 outflows above. The other 24 events are transfers into the treasury or between other parties.
  4. Read each amount as the 32-byte data word, base 1018.
  5. For each recipient, eth_getBalance at block 130605332 and at the chain head, plus eth_getTransactionCount and eth_getCode; binary-search the balance between block 1 and 130605332 for the first non-zero block.
  6. For the one address with BNB, read its first funded block in full and match the calldata amount to the balance delta.

Nodes used: public BSC JSON-RPC endpoints that serve historical state. Token decimals confirmed as 18 by calling decimals() (0x313ce567). Nothing in this audit depends on a block explorer’s labels; BscScan links are supplied only so every figure can be re-checked by eye.
